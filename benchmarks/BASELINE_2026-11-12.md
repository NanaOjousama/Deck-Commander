# AI efficiency — initial task-level baseline

**Project:** Deck Commander • **Tracking:** [Issue #2](https://github.com/NanaOjousama/Deck-Commander/issues/2) • **Date:** November 12, 2026 (Toronto local time; output timestamp was November 13 UTC).

**Verdict:** A repeatable benchmark was built and run against a separately launched copy of the existing gateway. **65/65 synthetic task runs passed**: 13 workflow variants with five repetitions each. No live gateway modifications, Windows configuration changes, user project reads, or secret recording.

## What we measured

These are **observable MCP-client** metrics: calls needed for a task, returned tool-text bytes, serialized tool-result bytes, task elapsed time (p50/p95), errors, empty polls, duplicate reads, and a simple bytes/4 approximate token proxy. Task-run IDs exist in private local JSON. This does *not* measure true ChatGPT context consumption, assistant token use, internal gateway-to-backend calls, or SSH subprocess counts.

## Results (medians of five samples)

| Synthetic task | Tool calls (baseline → alternative) | Tool-text UTF-8 bytes (baseline → alternative) | Elapsed time, ms (baseline → alternative) |
|---|---:|---:|---:|
| Repeated read of immutable fixture | 2 → 1 | 1,946 → 973 | 55 → 26 |
| Review eight synthetic notes | 8 → 1 | 7,784 → 127 | 220 → 111 |
| Latest line of synthetic log | 1 → 1 | 22,290 → 136 | 26 → 70 |
| Count 100 files | 1 → 1 | 2,099 → 119 | 11 → 76 |
| Count 1,000 files | 1 → 1 | 20,999 → 120 | 13 → 71 |
| Delayed process (1.35 s) | 2 → 1 | 241 → 120 | 1,428 → 1,451 |

Direct short command control: **1 call**, **117 bytes**, median **63 ms**.

### Observations

- Eight independent file reads became one bounded summary command for the narrow question “how many notes have the expected marker?” — eight to one client-facing call, from **7,784 to 127 bytes**; median elapsed fell from **220 ms** to **111 ms**. This does **not** prove one summarized command replaces full file reading when the user needs the actual file contents.
- Re-reading a **known immutable synthetic file** added an avoidable call and nearly doubled returned bytes; this is not a justification for caching live changing files without freshness checks.
- Latest log status: **22,290 vs 136 bytes** (about **99.4%** less response text), but bounded tail was *slower* in this sample (**70 vs 26 ms**). A native bounded log read could avoid extra subprocess startup.
- Counting 1,000 synthetic files returned **20,999 vs 120 bytes**, yet the native directory listing was *faster* (**13 vs 71 ms**). Compactness and latency must be balanced; do not eliminate detailed listing when the names are required.
- Smart Wait: median **2 → 1** MCP calls for a 1.35-second delayed process, with a similar overall task duration. The short-wait strategy produced **0 empty polls across five repetitions**, while Smart Wait produced **0**.

## Measurement limits

1. The harness is an **MCP client simulation**, not a recording of the ChatGPT model's real decision-making or hidden token counts. The derived `ceil(text bytes/4)` proxy is not an exact tokenizer.
2. Only text blocks returned to the harness count toward tool-text bytes; protocol bytes are tracked separately in local JSON. These measurements do not include the tool schema, developer instructions, host overhead, MCP initialization, reasoning, or network usage.
3. Five measurements per variant yield preliminary p50/p95 figures, not reliable service-level latency estimates. The harness uses Node.js and a fresh MCP client, after a warm-up command. Local system load, caching, filesystem and command launch overhead may vary.
4. This benchmark compares **strategies against one deployed gateway**, not two deployed builds. No before/after product improvement percentage is claimed.
5. Windows-off failure checks, interrupted transfers, internal gateway/backend traffic and SSH subprocess counts remain for a later instrumented benchmark pass. No need to power off the user’s computer to produce this initial baseline.

## Next benchmark-led engineering priorities

1. **Prototype one bounded, read-only inspection batch** with explicit typed requests, per-step limits and correctness receipts. Measure whether it combines multiple reads without the Python subprocess latency penalty; avoid exploding the exposed MCP tool count.
2. **Compact native responses and deterministic pagination:** small summaries with count, checksums/mtime, truncation signals and a drill-down cursor. Do not return 1,000 filenames when only a count is requested.
3. **Change-aware inspection:** a reliable freshness token before reusing prior results. Never assume a live file is unchanged just because a prior read was successful.
4. **Extend coverage:** simulated offline Windows, interrupted transfer workload, backend and SSH subprocess counters in an isolated harness, then compare calls and bytes per *successful* task after implementing a prototype.
5. **Do not change live gateway yet**; test output correctness and secure no-overwrite/host-key behavior, then deploy only if measurement and regression tests justify the changes.

## Reproduction and privacy

Run `node benchmarks/run.mjs --samples=5` with the SDK installed (see [harness README](README.md)). The script creates synthetic notes/logs and 100/1,000-file directories under a private temporary prefix and removes them. No prompts, real project filenames, API keys, network addresses, SSH credentials or user data are captured in the public report.
